# Mira ID 开放平台开发指南（V1 预览）

> 本指南描述目标接入体验，供狐邮、观澜、拾言及独立应用开发者讨论和准备。尚未发布 V1 SDK/API，不能按示例请求生产服务。规范唯一来源：[应用接入协议 V1](open-platform-protocol-v1.md)。现有第一方项目仍按 [V0 合同](service-registry-v0.md) 接入。

## 你可以做什么

任何 Mira ID 账号拥有者都可以开发应用并登记自己的部署实例。应用可以是你自己开发的，也可以是独立部署的同一个开源项目。你保有服务器、资源和业务数据；Mira ID 提供共同的身份、所有权登记、账号授权及终端服务发现。

Mira ID 并非 MCP 服务托管商、应用商店或业务代理。MCP 是首个服务接入 profile；开发者并不需要把所有应用包装成 MCP Server。

## 1. 部署你的应用

例如你和另一位开发者共同开发狐邮，两人分别部署：

| 项目 | 实例 A | 实例 B |
| --- | --- | --- |
| 应用项目 | who-you | who-you |
| 部署地址（示意） | https://mail-a.example | https://mail-b.example |
| APP_ID | 实例 A 自己生成 | 实例 B 自己生成 |
| AppSecret | A 的秘密管理环境 | B 的秘密管理环境 |
| 数据、授权与资源 | A 独立维护 | B 独立维护 |

CF Workers 只是一个部署选项，普通自建服务器同样适用。每个实例首次部署时生成并保存自己的身份和管理凭据；升级保留身份，复制为另一个实例时重新生成。不要把生产密钥写入项目源码、镜像、共享部署模板或提交到 Git。

## 2. 让应用能够自我描述

应用提供公开的机器可读发现文档（候选：`/.well-known/mira-application`）。完整字段、JSON 示例及校验语义见 [协议 §3](open-platform-protocol-v1.md#3-登记与发现候选-http-profile)。

开发者准备：

- 实例 APP_ID、项目标识、应用名称、描述、首页与图标；
- OAuth 客户端元数据及真实回调地址，候选采用独立的 HTTPS Client ID Metadata Document；
- 所有权验证端点，能证明对当前部署实例管理凭据的控制；
- 一个或多个服务描述：类型、协议版本、实际连接地址、资源标识、授权范围、适用终端；可提供描述与建议权重作为提示。

公开声明中没有 AppSecret。实例管理凭据、OAuth 客户端认证与用户/终端访问凭据必须分开。不要提交一份由人手工维护的工具 Schema 副本来替代 MCP 的实际发现能力。

## 3. 在 Mira ID 登记实例

目标界面：

```text
Mira ID → 我的应用 → 登记应用

应用地址  https://mail-a.example
APP_ID    [从自己的部署实例获得]
AppSecret [从自己的部署实例获得]

验证 → 预览应用与服务 → 登记
```

Mira ID 根据 [协议的所有权验证](open-platform-protocol-v1.md#32-所有权验证) 检查实例身份、地址、凭据及声明。登记通过后，在「我的应用」看到实例和服务信息。不能仅凭名称或公开 APP_ID 认领别人的实例；错误凭据、身份冲突、地址不一致须显式提示。

正常登记不需要额外开发者账号、管理员资格审批，也不需要开发者到 Mira ID 服务器运行 CLI。敏感信息只通过必要的验证通道传递，不能放在 URL、声明、日志或客户端持久存储中。

## 4. 接入通过 Mira ID 登录

应用网站提供「通过 Mira ID 登录」入口。候选接入采用 OAuth 授权码 + PKCE S256，应用负责生成 state/verifier，完成真实回调、校验 state/issuer 并在服务端兑换凭据。具体 OAuth endpoint 与登录凭据格式以最终协议和 SDK 为准。

- 用户在 Mira ID 的认证页面确认登录目标；应用不收集 Mira ID 用户密码。
- 成功主动登录该实例后建立账号使用授权；应用按自身业务策略决定用户可使用的数据及操作。
- 已登记的自己的实例不自动等于已使用的服务，仍按登录流程取得关联授权。
- 用户访问其他开发者的实例，也走相同的登录流程；不需要获得对方 AppSecret。
- 登录完成后应用建立自己的业务会话。应用专用登录凭据不能兑换其他服务、管理用户设备或冒充 Mira 原生终端。

实例应在用户确认的实际域名展示登录关系。别把 OAuth 登录失败、业务准入失败或声明过期伪装成成功授权。最终客户端认证、应用登录票据和业务准入交互尚待冻结，见 [协议 §4](open-platform-protocol-v1.md#4-oauth-登录与账号使用授权)。

## 5. 对 Mira 终端提供服务

应用登记本身不是每台手机/桌面的配置。用户成功授权后，所属有效 Mira 终端通过 Mira ID 获取账号关联目录，按自身支持的服务类型连接。

开发者只需提供自己的服务，并验证 Mira ID 签发、与本实例资源及权限匹配的访问凭据。不要要求终端上传 AppSecret、原始 Cloud Session 或邮件等业务系统的管理密钥。应用必须自行验证业务用户、数据归属与授权；被登记不等于可以越权访问或执行工具。

### MCP 服务（首个接入 profile）

1. 提供与目标 Mira 消费端兼容的 MCP HTTP endpoint，按实际协议协商版本；声明 type、protocol、resource、scope。
2. 受保护资源发布 RFC 9728 metadata，提供可信授权服务器发现；使用对应的 MCP Authorization 合同。根据最终 Mira profile 验证受众、签名/issuer、有效期、scope、subject 与资源绑定。
3. 正常响应 MCP 初始化和能力协商，通过 tools/list 暴露工具 schema（遵循分页和能力变化语义），按协议接收工具调用。若实现 resources/prompts，按对应协议能力暴露，不假定所有终端均支持。
4. 服务侧继续检查业务对象归属和操作授权。用户确认、工具治理与服务授权是不同层，不能把登记或 token 视为对任意高风险工具的批准。

其他类型尚未定义；不要为了通过登记而将非 MCP 服务伪装成 MCP，也不需要提前实现一个泛化工具框架。新类型出现时定义自己的 profile，复用已有应用身份、授权和服务目录。

## 6. 在 Mira ID 查看结果

| 关系 | 我的应用 | 关联服务 |
| --- | --- | --- |
| 自己部署并登记，但尚未登录授权 | 有 | 无 |
| 自己部署、登记且成功登录授权 | 有 | 有 |
| 登录并获准使用别人的部署实例 | 无 | 有 |
| 同一项目两个不同实例均获使用授权 | 仅显示自己登记的实例 | 两个实例分别展示 |

应用的名字可以相同；用域名与实例标识消歧。最终所有权移除、共同管理、分享准入、撤权交互与声明变化的授权策略以协议评审结果为准。

## 7. 接入自检清单

开发测试使用独立的测试账号和实例，不用生产数据。

- [ ] 两个部署使用同一项目，但拥有不同 APP_ID、AppSecret、回调与服务资源。
- [ ] 发现文档与凭据验证一致，不公开秘密，不接受任意回调或未验证来源。
- [ ] 自己的 Mira ID 可登记实例；另一账号无法未经授权取得管理权。
- [ ] 另一账号成功 OAuth 登录后能够使用获准服务，不获得所有权。
- [ ] 同账号 Mobile 与 Desktop 可以发现同一获准服务，各自使用对应的短期凭据。
- [ ] 两个实例不能相互接受错误受众/资源的访问凭据，业务数据仍相互隔离。
- [ ] MCP 的实际工具由服务返回；未知服务类型不会被自动当成工具或执行。
- [ ] 失效、撤权、重放与错误回调得到正确处理，升级不静默扩大授权。

完整验收标准与尚待决策项见 [协议 §7](open-platform-protocol-v1.md#7-实施前的未决问题与验收证据)。本指南不产生新的实现合同或部署授权。
