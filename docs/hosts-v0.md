# Mira Cloud Desktop Host Directory V0 (OPS-018)

This document specifies the minimal same-account Desktop Host presence directory
implemented by OPS-018. It builds on Mira Device and Cloud Session records. It
does not issue Relay tickets, grant Host tools, or verify Relay connections.

## Contract summary

A Desktop Host is an existing account-owned Mira Device with `platform =
"desktop"` that has advertised presence through an approved Desktop Cloud
Session. Cloud Auth owns the Host reference, the Relay room identifier, and the
presence lease. A caller cannot name its account, device, room, role,
availability, or owner.

The directory has two public endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/v1/hosts` | Register or refresh the caller's Host presence lease. Empty JSON body only. |
| `GET` | `/v1/hosts` | List the authenticated account's registered Hosts and current lease state. |

There is intentionally no public room-lookup route and no Relay ticket endpoint.

## Trusted Host caller contract

`POST /v1/hosts` requires an `Authorization: Bearer <Cloud Session>` that is all
of the following at the registration transaction boundary:

1. an active, non-revoked, non-expired Cloud Session with a matching secret
   hash;
2. an allowed, non-disabled account;
3. bound to a non-revoked `devices` row owned by the same account with
   `platform = "desktop"`;
4. backed by a consumed OPS-016 authorization code whose persisted `client_id`
   is the reviewed first-party `mira-desktop` client
   (`oauth_authorization_codes.consumed_by_session_id`).

The fourth condition is the persisted server-side OAuth client provenance from
OPS-016/OPS-017. It is not inferred from a request body, device `platform`, or
the mere possession of a bearer token.

Consequences:

- A Mobile OAuth session is rejected with `403 HOST_REGISTRATION_NOT_ALLOWED`
  even if it sends `platform=desktop` or `role=host`.
- A Portal/password Cloud Session is rejected even when it later becomes bound
  to a desktop Mira Device through `POST /v1/devices`.
- A caller cannot register or update another account's Host. Discovery is
  always scoped to the authenticated account; another account sees only its own
  entries.
- A revoked device, revoked session, logged-out session, disabled/denied
  account, or expired session cannot register or refresh a Host.

Trust boundary: public native OAuth client identifiers are not secrets, and V0
has no hardware proof-of-possession. This contract therefore proves that the
Cloud Session was issued through the reviewed `mira-desktop` authorization flow
and is currently bound to a desktop device; it does **not** cryptographically
prove that the running binary is an unmodified first-party Desktop build. An
actor who completes the first-party desktop authorization flow for their own
account can advertise that account's Host. This does not cross the account
boundary. Claiming stronger client attestation would require a separately
authorized work item.

## Presence and lease

Registration writes a server-timestamped lease. The default lifetime is 120
seconds, configurable by `MIRA_AUTH_HOST_LEASE_SECONDS` (reviewed range 30-3600
seconds). A Host must call `POST /v1/hosts` again before the lease expires to
remain available.

`GET /v1/hosts` returns:

```json
{
  "hosts": [
    {
      "id": "...",
      "deviceId": "...",
      "displayName": "Mira Desktop",
      "clientVersion": "1.0.0",
      "availability": "available",
      "relayRoom": "room_...",
      "registeredAt": "2026-10-25T12:00:00.000Z",
      "lastAdvertisedAt": "2026-10-25T12:00:30.000Z",
      "leaseExpiresAt": "2026-10-25T12:02:30.000Z"
    }
  ]
}
```

Readiness semantics:

| Signal | Meaning |
| --- | --- |
| Host row exists | The account has a registered Host record. |
| `availability = "available"` | A fresh server-observed Host lease exists, and the owning session, device and account are still active. |
| `availability = "offline"` | The Host is registered but its lease, session, device, or account is no longer active. |
| Network reachability | **Unknown.** Neither `available` nor any HTTP success proves that the Host or Relay is reachable. |

Device registration, account login, session restore, and `devices.last_seen_at`
are deliberately not used as Host readiness signals.

The directory output contains no Cloud Session token or hash, password material,
installation ID, device public key, Provider/MCP secret, filesystem path, tool
scope, or Host capability grant.

## Server-controlled Relay room

The room is generated by Cloud Auth from 256 random bits as
`room_<base64url>`. It is unique across all Host rows, bound to exactly one
account and device, and cannot be supplied or changed by a client. Refreshing
the lease for the same Host preserves the room. Registering the same device
again after a revocation rotates to a new room, so the old association does not
become valid again silently.

For OPS-019 and the G2 Host Grant work (OPS-020), the server-side input is:

```ts
hostService.resolveRoomOwnership(room):
  | {
      hostId: string;
      accountId: string;
      deviceId: string;
      relayRoom: string;
      availability: "available" | "offline";
      lastAdvertisedAt: string;
      leaseExpiresAt: string;
    }
  | null
```

`null` means the room has no current owner (unknown, revoked Host, or revoked
device). A non-null result with `availability = "offline"` still names the
owner but must not be treated as online. OPS-019 uses this input for its ticket
entitlement decision (see [service-credentials-v0.md](service-credentials-v0.md));
OPS-018 neither signs nor authorizes a Relay ticket.

## Revocation and cleanup

- Logging out revokes the Cloud Session. A database trigger immediately revokes
  the Host row currently owned by that session.
- Device revocation revokes the Host row and all bound sessions. The old room
  no longer resolves.
- Password change, account deny, and account disable revoke sessions, which in
  turn revoke the associated Host rows.
- Lease expiry marks the Host `offline` without granting it or any other caller
  new authority. A later registration from a still-valid session renews it.
- Presence state is persisted in SQLite and survives process restart. Store
  times are UTC ISO-8601 strings; lease decisions use an injected server clock
  in tests and the real clock in the service.

## Persistence

Migration `006_desktop_hosts.sql` adds `desktop_hosts`:

- server-generated `id`, `device_id`, and unique `relay_room`;
- owning `account_id` and the advertising `session_id`;
- `created_at`, `advertised_at`, `lease_expires_at`, `updated_at`;
- `revoked_at` and `revoke_reason`;
- one row per device, indexes for account discovery and session/room lookup.

Revocation triggers are part of the storage boundary so every existing session
or device revocation path has the same Host effect.

## Verification

- T1 unit: lease/availability matrix and room shape/uniqueness.
- T2 Fastify inject: Host registration, same-account discovery, cross-account
  isolation, forged account/room/role/platform rejection, Mobile and Portal
  caller rejection, two-account room separation.
- T3 SQLite: reopen persistence, lease timeout and refresh, logout/device
  revocation, old-room invalidation, re-registration with rotated room, and
  one-row consistency for two sessions registering the same device.
- `pnpm run check` covers the repository-wide typecheck and test gate.

Readiness attributes with observable signal are limited to the server-stored
Host lease, the owning Cloud Session state, the device revocation state, and the
account admission state. No test or response claims real Host/Relay reachability.

## Out of scope

- Relay room-role ticket entitlement (OPS-019).
- G2 Host Grant and `tools:invoke` authorization (OPS-020; see [host-grants-v0.md](host-grants-v0.md)).
- Portal grant management (OPS-021).
- Remote Gateway, Harness, transport service, or Relay connection changes.
- Distributed heartbeat infrastructure, media/payload persistence, or reverse
  Mobile-device capability exposure.
- Public room enumeration, public room ownership lookup, OAuth provider work,
  hardware proof-of-possession, or a general OAuth framework change.
